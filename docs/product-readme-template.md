# TRLX product README format

Use this structure for product repositories. Write for a first-time user deciding whether the product solves their problem. Keep deeper implementation details in linked documentation. Adapt the language to the audience; technical product repositories default to English.

## Recommended order

1. **Product image:** an original, legible banner with the exact product name, visual identity and one clear benefit. Store the asset in the repository. Keep the essential message available as text and alt text.
2. **Name and promise:** a recognizable name and one sentence describing the outcome. Distinguish the product from a generic category or acronym.
3. **Problem and fit:** describe the user's current friction and how this product helps. Make the target user clear without a long origin story.
4. **Useful outcomes:** four to six capabilities expressed as questions the user can answer or jobs they can complete. Technical features support the benefits.
5. **First workflow:** one real command or interaction and a short explanation of its result. Label illustrations and synthetic examples. Separate collection from interpretation when they are different components.
6. **Quick start:** prerequisites, installation, essential setup, first success. Every copyable command must work in the documented environment. Explain placeholders, account access and manual steps.
7. **Integrations and control:** explain how the product fits the user's existing tools and what choices remain theirs. Link configuration details.
8. **Trust and limits:** state verification, release maturity, material data/cost boundaries and known operational limits. Link the evidence. Keep internal deployment history and conversations out of the public-facing copy.
9. **Next steps:** a short documentation map and one useful call to action, such as trying the workflow or reporting an issue.
10. **Attribution and license:** identify the maintainer, third-party affiliations and actual distribution terms. Repository visibility does not imply an open-source license.

## Editorial acceptance check

- The opening explains the product and its value without reading a command reference.
- The name, banner, metadata and links use consistent branding.
- The visual remains readable at GitHub content width and contains no personal account data.
- Benefits correspond to implemented behavior. No invented savings, endorsements, metrics or guarantees.
- A first-time user can find prerequisites, installation and first success quickly.
- Examples, live observations and model-generated interpretation are distinguished.
- Detailed commands, troubleshooting and verification are one click away.
- Links and packaged assets resolve; images and formatting have been inspected in a rendered preview.
- Support instructions do not request secrets or private browser state.
- The final change is committed, pushed and checked at the resulting GitHub commit.

This is a presentation standard, not a numerical certification of product reliability. Improve the copy and evidence instead of assigning an unsupported readiness score.
